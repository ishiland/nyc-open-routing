# Milestone v2.2: Edge Isochrones & Waypoints

**Status:** SHIPPED 2026-02-14
**Phases:** 9-12
**Total Plans:** 8

## Overview

Add edge-based isochrone visualization (colored street segments by travel time) and multi-stop waypoint routing (A to B to C). Two independent features that extend the existing routing and reachability capabilities.

## Phases

### Phase 9: Edge Isochrone SQL

**Goal**: Isochrone SQL functions produce reachable street geometries colored by travel time, not just hull polygons
**Depends on**: Nothing (builds on existing isochrone SQL functions)
**Requirements**: ISO-01
**Plans**: 1 plan

Plans:
- [x] 09-01: Create and validate edge-based isochrone SQL functions for all three modes

**Success Criteria:**
1. SQL isochrone functions return edge geometries (LineStrings) with cumulative travel time for each reachable street segment
2. Edge results include street name, travel time, and band index for downstream rendering
3. Functions work for all three modes (drive, bike, walk) and respect traffic settings when applicable

### Phase 10: Edge Isochrone Frontend

**Goal**: Users can see exactly which streets are reachable within each time band, rendered as colored line segments on the map
**Depends on**: Phase 9
**Requirements**: ISO-02, ISO-03, ISO-04
**Plans**: 2 plans

Plans:
- [x] 10-01: Add edge isochrone API support (schemas, service method, view query parameter)
- [x] 10-02: Wire edge isochrone into frontend (types, context, map layer, toggle UI, legend)

**Success Criteria:**
1. User can toggle between polygon view and edge-based view for isochrones
2. Reachable streets display as colored lines with distinct colors per time band (5/10/15/20 min)
3. Edge-based isochrones render correctly for drive, bike, and walk modes
4. Traffic toggle affects edge-based isochrone results in drive mode
5. Line width and visibility scale appropriately across zoom levels

### Phase 11: Waypoint Routing Backend

**Goal**: The routing engine calculates ordered multi-stop routes through intermediate waypoints with per-leg turn directions
**Depends on**: Nothing (independent of edge isochrone work)
**Requirements**: WAY-02
**Plans**: 2 plans

Plans:
- [x] 11-01: Pydantic response models + RoutingService.get_waypoint_route method (leg assembly)
- [x] 11-02: /api/route/waypoints endpoint + unit tests (service + route layer)

**Success Criteria:**
1. Service layer accepts list of waypoints and calls existing SQL routing functions sequentially per leg
2. API endpoint accepts a list of waypoints and returns a route response with per-leg directions and summaries
3. Multi-stop routing works for all three modes (drive, bike, walk)
4. Existing two-point routing continues to work unchanged

### Phase 12: Waypoint Routing Frontend

**Goal**: Users can build multi-stop routes by adding and removing intermediate waypoints in the sidebar, with markers visible on the map
**Depends on**: Phase 11
**Requirements**: WAY-01, WAY-03, WAY-04
**Plans**: 3 plans

Plans:
- [x] 12-01: Waypoint types, context state, fetch hook, WaypointSearch component
- [x] 12-02: Wire Sidebar, ButtonControls, MapLibreGLMap, RouteList, RouteSummaryCard for waypoints
- [x] 12-03: Human verification of end-to-end waypoint routing

**Success Criteria:**
1. User can add intermediate waypoints between origin and destination via the sidebar
2. Each waypoint appears as a numbered marker on the map at the correct location
3. User can remove any individual waypoint and the route recalculates
4. Turn-by-turn directions in the sidebar are grouped by leg
5. Existing two-point routing UX remains unchanged when no waypoints are added

## Milestone Summary

**Key Decisions:**
- ST_SimplifyPreserveTopology 1-foot tolerance (SRID 2263) for edge geometry simplification
- DISTINCT ON (eid) ORDER BY agg_cost for deduplicating edges reached from multiple directions
- Exclusive band assignment: each edge in exactly one band to prevent duplicate rendering
- Union type for IsochroneResponse.features to support both polygon and edge features
- Separate cache prefix iso-edges- to prevent polygon/edge cache collisions
- Clear isochrone data on view switch to force re-fetch with correct view parameter
- Edge line width scales 1px->4px across zoom 10->16 for clarity at all scales
- Leg index on LegResponse not on Feature properties to avoid modifying existing Properties model
- Waypoint routing delegates to existing mode-specific methods per leg (no new SQL)
- Separate useWaypointRouteFetch hook to preserve existing routing unchanged
- addWaypoint enforces max 1 intermediate waypoint matching backend 3-total-point constraint
- RouteList uses three-state conditional: waypointRoute -> regular route -> empty state

**Issues Resolved:**
- Stale waypointRoute data persisted when removing waypoints (fixed by clearing before regular route dispatch)
- IsochroneResponse union type compilation errors required type narrowing in legend code

**Issues Deferred:**
- Waypoint suggestion dropdown z-index can overlap with To field recent searches dropdown (cosmetic)
- Edge-based isochrone payload size at scale (5K-15K edges) may need geometry simplification

**Technical Debt Incurred:**
- None significant
